# Resumen de Implementación v0.9.0 — Arquitectura de Memoria Asociativa Multiresolución

## 1. ¿Qué cambió?

### Problemas resueltos en v0.9.0

| Problema | Causa raíz | Solución |
|---|---|---|
| Error `413 Request too large` (Groq) | `MemorySummarizer` y `EvolutionDetector` competían con el chat por la cuota TPM de Groq | Migrados a Gemini Flash (ADR-0029). Groq queda 100% reservado para respuestas conversacionales |
| RAG inyectaba teoría clínica incluso en saludos | Los tools de Chat y TCC recuperaban siempre 3+2 fragmentos sin filtrar por intent | Nodo `context_retriever` en LangGraph salta la búsqueda semántica en intents casuales (saludos, despedidas) |
| Hechos contradictorios sin orden temporal | Time Decay documentado pero no implementado en `hybrid_search.py` | Two-Stage Retrieval: Top-100 → re-ranking con $Score = Similitud \times e^{-0.01 \cdot \Delta t_{dias}}$ (ADR-0030) |
| Bóveda de conocimiento como JSON blob chunkeado | `save_knowledge()` serializaba el dict completo al chunker | Ingesta atómica: cada hecho es un registro independiente con su embedding (ADR-0032) |
| Recuperaciones duplicadas entre especialistas | RAG se calculaba dentro de cada tool, invisible al orquestador | `RagContextSnapshot` en `GraphStateV2`. Nodo `context_retriever` único (ADR-0031) |
| Sin relaciones entre dominios | No existía tabla de aristas ni búsqueda multi-salto | Tabla `memory_edges` + CTE recursivas en SQLite, máximo 2 saltos (ADR-0033) |
| Namespace `"user"` compartido | `IngestionPipeline` hardcodeaba `namespace="user"` | Namespace dinámico: `user_{chat_id}` (ADR-0032) |

### Bugs encontrados y corregidos post-deploy

| Bug | Síntoma | Causa | Fix |
|---|---|---|---|
| **Error de routing asíncrono** | `"object str can't be used in 'await' expression"` | `initial_router_with_context_retriever` era `async def` pero LangGraph `add_conditional_edges` requiere funciones síncronas | Commit `23e9c86` — removido `async`/`await` |
| **Crash en format_knowledge_for_prompt** | `AttributeError: 'str' object has no attribute 'get'` | `context_retriever` serializaba listas como strings. `format_knowledge_for_prompt` recibía caracteres sueltos | Commit `a23fee5` — extracción correcta de vault sections + formateo directo |
| **Intent no propagado** | `context_retriever` siempre veía `intent='unknown'` | `routing_utils` guardaba intent en `payload["intent"]` pero `context_retriever` leía de `payload["routing_metadata"]["intent"]` | Commit `6c7e420` — escribir intent en ambos lugares |
| **Bug crítico: Analytical Intents no existen** | Graph-RAG nunca se ejecuta | Los intents `life_review`, `pattern_analysis`, `cross_domain_query` hardcodeados en `context_retriever.py` **no existen en el enum `IntentType`**. El Graph-RAG es código muerto. | Pendiente (A.4 en Plan Maestro) |

## 2. Pipeline de mensajería actual

```
Telegram → Webhook → CanonicalEventV1
  → MasterOrchestrator.run()
    → meta_router (enrutamiento inicial)
         └── ¿vulnerabilidad? → routing directo a CBT
         └── ¿otro? → LLM analiza y asigna especialista
      → initial_router_function
           └── ¿especialista conocido? → context_retriever
           └── ¿otro? → fin
        → context_retriever (NUEVO)
             ├── Cargar evolution_note de Redis
             ├── Búsqueda vectorial (sqlite-vec) → fragmentos globales + usuario
             ├── Reranker semántico (Gemini API) → Top-4
             ├── Graph-RAG (SOLO si intent analítico → bug, nunca se ejecuta)
             ├── Hechos estructurados (confianza ≥ 0.7)
             └── Depósito en state["rag_context"]
        → especialista (chat, tcc, etc.)
             └── Lee state["rag_context"] en lugar de llamar a SQLite/Redis
        → chain_router → END
    → Respuesta → Telegram
  [BACKGROUND] store_raw_message → buffer Redis
    → [cada 5 mensajes] extracción incremental de facts
    → [10 msgs o 30 min] ConsolidationManager
         ├── MemorySummarizer (Gemini)
         ├── FactExtractor (Gemini) → save_knowledge atómico
         ├── EvolutionDetector (Gemini)
         ├── Cache de Nota Evolutiva en Redis (TTL 24h)
         └── _generate_transversal_edges (Gemini)
              └── Analiza hechos + conversación → crea memory_edges
```

## 3. Arquitectura de almacenamiento (Local-First)

El sistema corre 100% en GCP pero almacena los datos **localmente en el disco de la VM**, no en servicios cloud de Google. Esta fue una decisión deliberada documentada en ADR-0017 ("Cero dependencia de GCS").

```
                    ┌──────────────────────────────────┐
                    │       GCP VM (instancia)          │
                    │                                  │
                    │  ~/AEGEN/storage/                │
                    │    ├── aegen_memory.db (SQLite)  │
                    │    ├── knowledge/ (PDFs)          │
                    │    └── backups/                   │
                    │                                  │
                    │  Redis (contenedor Docker)        │
                    │  └── redis_data:/data             │
                    │                                  │
                    │  Google Gemini API ──────────────┼── Solo embeddings
                    └──────────────────────────────────┘
```

### Datos encontrados en GCP (producción)

```
chat_id=6095416210, type=conversation → 15 registros
chat_id=6095416210, type=document    → 53 registros
chat_id=6095416210, type=fact        → 439 registros (formato legacy JSON blob)
chat_id=system,      type=document    → 31 registros (PDFs TCC + DSM-5)
```

Los 439 facts del usuario están en formato JSON blob (pre-ADR-0032). No son accesibles por el RAG semántico nuevo porque el contenido es JSON serializado, no texto natural. **Pendiente:** ejecutar `make migrate-facts` para convertirlos a atómicos.

### Backup

GCS backup **nunca fue activado** (`GCS_BACKUP_BUCKET = None`). El código de `CloudBackupManager` existe y es funcional. Pendiente en Plan Maestro (A.7).

## 4. Bugs y problemas pendientes descubiertos

### Bug crítico: Analytical Intents no existen en IntentType

**Archivos:** `src/core/routing_models.py` vs `src/agents/orchestrator/context_retriever.py`

El `IntentType` enum define estos intents:
`CHAT, FILE_ANALYSIS, SEARCH, HELP, TASK_EXECUTION, INFORMATION_REQUEST, PLANNING, DOCUMENT_CREATION, VULNERABILITY, TOPIC_SHIFT, PSICOTRADING`

El `context_retriever.py` hardcodea:
```python
analytical_intents = {"life_review", "pattern_analysis", "cross_domain_query"}
```

**Ninguno de esos 3 existe en el enum.** El Graph-RAG por intents analíticos es código muerto. Nunca se ejecutó ni se ejecutará.

**Adicional:** `routing_tools.py` tiene un `Literal` con 10 intents pero falta `psicotrading` que sí existe en el enum. Hay que mantener sincronizados 4 archivos manualmente para cualquier cambio.

**Solución propuesta (A.4 en Plan Maestro):** Eliminar la dependencia de intents para Graph-RAG. Reemplazar por detección data-driven: si los fragmentos recuperados tienen aristas en `memory_edges`, expandir el grafo. Sin esperar intents analíticos.

### Minimax/OpenRouter: ¿Por qué se usó?

Los logs mostraban:
```
LLM call completed: provider=OpenRouter, model=minimax/minimax-m2.5:free, latency=3052.6ms, tokens=6479
```

La auditoría del `engine.py` reveló que Minimax es solo el **fallback** de `get_analytical_llm()`. El primario es Groq (`gpt-oss-120b`). Si se usó Minimax en producción, significa que **Groq falló o fue más lento** para esa llamada específica. Pendiente investigar (A.10 en Plan Maestro).

### El problema del "apagarme" (guardrails clínicos)

El usuario reportó respuestas repetitivas con "Línea 106 (Colombia)" incluso cuando la mención fue metafórica. El sistema **no tiene detección de crisis a nivel de código** — solo confía en el LLM a través de `CLINICAL_GUARDRAILS` inyectados en el prompt de CBT.

Cuando el usuario dijo "apagarme", el LLM interpretó literalmente y activó los recursos de crisis. La solución está en **B.6** del Plan Maestro: implementar detección semántica a nivel de código y guardrails contextuales.

## 6. Inteligencia temporal: estado actual

### Lo que existe
- Hora local del usuario inyectada en el prompt (Layer 5 del Soul Stack)
- Timezone configurable por usuario
- Time Decay en ranking de búsqueda (`MEMORY_DECAY_LAMBDA`)
- Session TTL adaptativo en Redis (4h-24h según tipo)

### Lo que falta (B.7 en Plan Maestro)
- Duración de la sesión en el prompt (MAGI no sabe cuánto lleva hablando)
- Patrones temporales: "los lunes estás más ansioso"
- Conciencia de calendario: festivos, estaciones
- Antigüedad visible de los hechos para el LLM

## 7. Observabilidad: estado actual y fallos

### Lo que existe
- 5 métricas Prometheus (`llm_calls_total`, `llm_tokens_total`, `llm_latency_seconds`, `llm_active_calls`, `llm_cost_total`)
- Endpoint `/metrics` expuesto vía `prometheus-fastapi-instrumentator`
- Endpoints REST: `/system/health`, `/system/llm/status`, `/system/llm/metrics/summary`
- Correlation IDs en cada request

### Fallos conocidos (C.5 en Plan Maestro)
1. `metrics_processor.py` solo detecta `ChatGoogleGenerativeAI` — Groq y OpenRouter aparecen como `provider="unknown"`
2. Costos solo estimados para Gemini; Groq/OpenRouter no se contabilizan
3. Endpoint `/system/llm/metrics/summary` tiene valores hardcodeados (latencia 0.0, timestamp fijo)
4. No existe dashboard (Grafana) para visualizar métricas en tiempo real
5. No hay alertas automáticas cuando un componente falla
