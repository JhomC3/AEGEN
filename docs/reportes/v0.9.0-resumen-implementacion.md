# Resumen de Implementación v0.9.0 — Arquitectura de Memoria Asociativa Multiresolución

## 1. ¿Qué cambió?

### Problemas resueltos

| Problema | Causa raíz | Solución |
|---|---|---|
| Error `413 Request too large` (Groq) | `MemorySummarizer` y `EvolutionDetector` competían con el chat por la cuota TPM de Groq | Migrados a Gemini Flash (ADR-0029). Groq queda 100% reservado para respuestas conversacionales |
| RAG inyectaba teoría clínica incluso en saludos | Los tools de Chat y TCC recuperaban siempre 3+2 fragmentos sin filtrar por intent | Nodo `context_retriever` en LangGraph salta la búsqueda semántica en intents casuales (saludos, despedidas) |
| Hechos contradictorios sin orden temporal | El Time Decay estaba documentado pero no implementado en `hybrid_search.py` | Two-Stage Retrieval: Top-100 por similitud → re-ranking con $Score = Similitud \times e^{-0.01 \cdot \Delta t_{dias}}$ (ADR-0030) |
| Bóveda de conocimiento almacenada como JSON blob chunkeado | `save_knowledge()` serializaba el dict completo y lo pasaba al chunker | Ingesta atómica: cada hecho (`fact_key: valor`) es un registro independiente con su propio embedding (ADR-0032) |
| Recuperaciones duplicadas entre especialistas | El RAG se calculaba dentro de cada tool, invisible al orquestador | `RagContextSnapshot` en `GraphStateV2`. Nodo `context_retriever` ejecuta la recuperación una sola vez (ADR-0031) |
| Sin relaciones entre dominios | No existía tabla de aristas ni búsqueda multi-salto | Tabla `memory_edges` + CTE recursivas en SQLite para Graph-RAG con máximo 2 saltos (ADR-0033) |
| Namespace `"user"` compartido entre todos los usuarios | `IngestionPipeline` hardcodeaba `namespace="user"` | Namespace dinámico: `user_{chat_id}` aísla memorias por usuario |

## 2. Cómo funciona ahora el pipeline de mensajería

```
Telegram → Webhook → CanonicalEventV1
  → MasterOrchestrator.run()
    → meta_router (enrutamiento inicial)
      → context_retriever (NUEVO)
           ├── ¿intent casual? → solo evolution_note de Redis (0ms), sin RAG
           └── ¿intent analítico o clínico?
                ├── Búsqueda vectorial (sqlite-vec)
                ├── Reranker semántico (Gemini API) → Top-4
                ├── Graph-RAG (expansión de grafo a 2 saltos) si intent analítico
                ├── Hechos estructurados (confianza ≥ 0.7)
                └── Depósito en state["rag_context"]
      → especialista (chat, tcc, etc.)
           └── Lee state["rag_context"] en lugar de llamar a SQLite/Redis
      → chain_router → END
    → Respuesta → Telegram
  [BACKGROUND] store_raw_message → buffer Redis
    → [cada 5 mensajes] extracción incremental de facts
    → [10 msgs o 30 min] ConsolidationManager
         ├── MemorySummarizer (ahora Gemini, no Groq)
         ├── FactExtractor (Gemini) → save_knowledge atómico
         ├── EvolutionDetector (ahora Gemini)
         ├── Cache de Nota Evolutiva en Redis (TTL 24h)
         └── _generate_transversal_edges (NUEVO)
              └── Gemini analiza hechos + conversación → crea memory_edges
```

### Intents que activan Graph-RAG (expansión de grafo)

Solo los siguientes intents ejecutan la búsqueda multi-salto en `memory_edges`:
- `life_review`
- `pattern_analysis`
- `cross_domain_query`

Cualquier otro intent (chat casual, CBT, etc.) no expande el grafo, manteniendo latencia baja.

## 5. Tareas post-deploy recomendadas

### Inmediatas (al hacer pull en GCP)

1. **Ejecutar migraciones de schema**: Las migraciones son idempotentes y se ejecutan automáticamente en cada arranque de FastAPI (lifespan). Verificar en logs: `"Migration: index check complete"`.
2. **Migrar facts legacy** (si existen usuarios con datos previos):
   ```bash
   make migrate-facts
   ```
   Este script escanea la DB, parsea blobs JSON legacy y los reingesta como hechos atómicos individuales. Los blobs originales se marcan `is_active=0` (soft delete).

### Monitoreo (primeros 30 días)

- **Calibración de λ (MEMORY_DECAY_LAMBDA)**: Si los usuarios reportan que MAGI "olvida" información relevante demasiado rápido, reducir λ (ej. `0.005`). Si las memorias antiguas siguen apareciendo con mucho peso, aumentar λ (ej. `0.02`).
- **Reranker**: El reranker hace una llamada a Gemini Flash por cada mensaje no-casual. Monitorear costos de API. Si el volumen es alto, se puede desactivar retornando los candidatos RRF directamente desde `semantic_fragments`.
- **memory_edges**: La tabla `memory_edges` nace vacía. Crece orgánicamente con cada sesión de consolidación (~10 mensajes). Tras las primeras 24h, verificar con:
  ```sql
  SELECT COUNT(*) FROM memory_edges;
  ```
