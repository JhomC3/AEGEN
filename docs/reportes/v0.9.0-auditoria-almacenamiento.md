# Reporte de Almacenamiento — Auditoría de Datos v0.9.0

## Arquitectura de Almacenamiento (Local-First por ADR-0017)

El sistema corre 100% en GCP pero almacena los datos **localmente en el disco de la VM**, no en servicios cloud de Google (GCS, Firestore, etc.). Esto fue una decisión arquitectónica deliberada documentada en ADR-0017 ("Cero dependencia de GCS").

```
                    ┌──────────────────────────────┐
                    │       GCP VM (instancia)      │
                    │                               │
                    │  ~/AEGEN/storage/             │
                    │    ├── aegen_memory.db ◄──────┼── SQLite (bind mount)
                    │    ├── knowledge/ (PDFs)      │
                    │    └── backups/               │
                    │                               │
                    │  Redis (contenedor Docker)    │
                    │  └── redis_data:/data ◄───────┼── Sesiones/cache (volumen)
                    │                               │
                    │  Google Gemini API ───────────┼── Solo embeddings (API externa)
                    └──────────────────────────────┘
```

**La DB no está en un servicio cloud de Google.** Está en el disco de la VM, en `~/AEGEN/storage/aegen_memory.db`. Docker la monta como bind mount (`./storage:/app/storage`). Si la VM se destruye, los datos se pierden **a menos que** se active el backup a GCS.

### Problema detectado: Facts en formato legacy

Los 439 facts del usuario están almacenados como **JSON blobs** (el formato anterior a ADR-0032). Cada registro contiene un chunk de ~400 tokens del JSON serializado de la bóveda, no un hecho atómico individual.

Esto causa que el RAG semántico no encuentre estos facts porque:
1. El contenido es JSON, no texto natural → el embedding no se parece semánticamente a frases como "últimamente estoy irritable"
2. No tienen `fact_key` individual → el nuevo `context_retriever` no puede filtrarlos
3. Están mezclados con metadatos de serialización

**Solución:** Ejecutar `make migrate-facts` para convertir cada hecho individual en un registro atómico independiente con su propio embedding.

## Esquema de almacenamiento actual

| Dato | Dónde se guarda | Persistencia |
|---|---|---|
| Fragmentos de conocimiento global (PDFs) | `memories` con `chat_id='system'` | Permanente (SQLite) |
| Hechos del usuario (facts legacy) | `memories` con `memory_type='fact'` | Permanente (SQLite) — **migrar a atómico** |
| Hechos del usuario (atómico) | `memories` con `fact_key` en metadata | Permanente (SQLite) |
| Conversaciones | `memories` con `memory_type='conversation'` | Permanente (SQLite) |
| Relaciones entre dominios | `memory_edges` | Permanente (SQLite) |
| Perfiles de usuario | `profiles` | Permanente (SQLite) |
| Vectores semánticos | `memory_vectors` (sqlite-vec) | Permanente (SQLite) |
| Caché de embeddings | `embedding_cache` | Permanente (SQLite) |
| Sesiones activas | Redis `chat:session:{chat_id}` | TTL 24h |
| Buffer de mensajes | Redis `chat:messages:{chat_id}` | Volátil (cap 50) |
| Resumen de largo plazo | Redis `chat:summary:{chat_id}` | Permanente (SQLite + Redis) |
| Nota evolutiva | Redis `chat:evolution_note:{chat_id}` | TTL 24h |
| Respaldos GCS | ❌ No activado | — |
